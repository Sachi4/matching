# 運命の出会いを科学する

同じ刺激を見た者同士の"感じ方の共鳴"を可視化し、会場に即興のつながりを生むツール。
AIAU Craft Day（2026年8月14〜16日）でのライブ体験用MVP。

> 同じものを見て、同じように心が動いた。
> その偶然を、会場でその場で見つけられるようにする。

イベント会場で同じ刺激（画像）を見た参加者の「感じ方」を比べ、**共鳴**が起きたペアを
リアルタイムに可視化するツール。約70名規模のハッカソン会場でのライブ体験用に3日間で開発した。

---

## コンセプト

### 解きたいこと

大人数の会場で「話が合う人」に出会えるかは、ほぼ席順と度胸で決まる。
プロフィール（所属・職種・趣味）で人をつなぐ既存のマッチングは、
**属性が似ている人**を見つけられても、**感じ方が似ている人**は見つけられない。

そこでこの体験では、自己紹介ではなく「同じ画像を見たときの反応」を手がかりにする。
肩書きを知らないまま、感性の近さだけで相手が浮かび上がる状態をつくる。

### 3つの考え方

1. **共通の刺激から始める** — 質問に答えるのではなく、全員が同じ画像を見る。
   同じ入力に対する反応の差分だから、比較に意味が出る。
2. **感じ方を数値にする** — 自由記述の感想を embedding に変換し、類似度を「共鳴度」という
   ひとつの数字にまとめる（[共鳴のしくみ](#共鳴のしくみ)）。
3. **会場に還す** — 数値は本人に返すのではなく、共鳴フィードと星座UIに流す。
   自分のペアが名前つきで会場に映ることが、話しかけるきっかけになる。

### 大切にした設計判断

- **認証なし・ニックネームのみ** — 参加の摩擦をゼロにする。データはイベント限りの使い捨て。
- **相性の点数は出さない** — 「あなたと◯◯さんは82%」ではなく、
  ペアごとに生成される詩的な**反応名**（例:「とけていく夕暮れ」）だけを見せる。
  評価ではなく話の入口を渡すため。
- **診断ステップを持たない** — 開発初期は感性診断（6問）を挟む設計だったが、実際に動かして
  みたところ、質問に答えるステップが体験のテンポを損ない、画像を見た直後の直感的な反応から
  離れてしまうことが分かった。このプロダクトが目指すのは「じっくり内省する」体験ではなく
  「素早く反応し合う」ことで会場を盛り上げる体験だと判断し、診断ステップを撤廃。
  画像への感想（embedding類似度）だけでマッチングする、より単純な仕組みに作り直した。
- **AIキーなしでも動く** — embedding も反応名生成もフォールバック実装があり、
  会場のネットワークやAPI障害で体験が止まらない（[フォールバック](#aiキーなしでの動作)）。
- **チューニングはSQLだけで完結** — 会場の熱量を見ながら、共鳴の閾値をその場で緩められる。

### 用語

| 用語 | 意味 |
| --- | --- |
| 刺激 (stimulus) | 全員に見せる画像。会場で順番に切り替える |
| 感想 (response) | 形容詞チップ + ひとこと自由記述 |
| 共鳴度 (resonance) | 2人の感想の近さを表すスコア（0〜1） |
| 反応名 | 共鳴したペアに与えられる詩的な短句。Claudeが生成 |
| 共鳴フィード | 成立したペアが流れていくライブなタイムライン |
| 星座UI | 自分を中心に、他の参加者との感じ方の近さを距離で表現するインタラクティブな可視化 |

## 体験フロー

1. `/` … ニックネーム登録（認証なし）
2. `/respond` … 画像を見て感じたことを記録（形容詞チップ + ひとこと自由記述）。用意した
   複数の画像それぞれについて繰り返す
3. `/feed` … 星座UI + 共鳴フィード（スマホ用）。共鳴が発生すると、画面を占有する演出とともに
   相手のニックネームが表示され、星座UI上の該当ペアがハイライトされる
4. `/screen` … 会場の大画面用ビュー
5. `/admin/stimuli` … 運営用: 刺激画像の追加・表示切替・削除

## 3日間の開発ハイライト

限られた時間の中で、以下の試行錯誤を経てこの形にたどり着いた。

- **UI設計の反復**：当初は物理的な座席位置に基づく会場マップを検討したが、会場レイアウトが
  流動的なため撤回。カード型の結果表示 → 星座UI（距離による可視化）→ モザイクウォール案、と
  複数のビジュアル表現を比較検討し、最終的に「自分を中心に据えた距離表現」と「画面占有型の
  発見演出」の組み合わせに着地した
- **体験フローの簡略化**：診断ステップを設けていたが、実機テストでテンポの悪化が判明し撤廃。
  「画像を見て、感じたことを記録する」というシンプルな繰り返しに一本化した
- **テスト基盤の整備**：実際の参加者データを待たずに共鳴の発生を検証できる、強制ペア投入・
  強制マッチ投入の仕組みを構築。これにより実装のその場での検証サイクルを高速化した
- **信頼性の担保**：会場のネットワークやAPIキーの問題で体験が止まらないよう、embedding生成・
  反応名生成の両方にフォールバック実装を用意した

## 技術スタック

- **フロントエンド**：Next.js (App Router)、Tailwind CSS
- **バックエンド/DB**：Supabase（Postgres、pgvector、Realtime、Edge Functions）
- **embedding生成**：OpenAI `text-embedding-3-small`（マルチモーダル埋め込みとしてGemini APIも
  併用可能。キー未設定時はフォールバックあり）
- **反応名生成**：Anthropic Claude（`claude-3-5-haiku`。キー未設定時はフォールバックあり）
- **ホスティング**：Vercel
- **開発**：Devin（自律型AIコーディングエージェント）を用いて実装

## アーキテクチャ

- フロントエンド: Next.js (App Router) + Tailwind CSS
- バックエンド/DB: Supabase (Postgres + pgvector + Realtime + Edge Functions)
- 感想投稿の流れ:
  1. フロントが Edge Function `submit-response` を呼ぶ
  2. Edge Function が感想文の embedding を生成（OpenAI `text-embedding-3-small`。キー未設定時は
     簡易フォールバック。Gemini マルチモーダル埋め込みを組み合わせる場合は画像情報も加味）
  3. `stimulus_responses` に insert
  4. DB関数 `find_resonance_candidates` が同じ画像を見た他参加者との共鳴度を計算
  5. 閾値を超えたペアを `matches` に insert し、Claude API で「反応名」（詩的な短句）を生成
- フロントは Supabase Realtime（`postgres_changes`）で `matches` / `stimulus_responses` の insert を
  購読し、共鳴フィードと星座UIを即時更新する
- 感想投稿から共鳴判定までは非同期処理とし、参加者は待たされることなく次の画像に進める

### 共鳴のしくみ

```
共鳴度 = embedding類似度（感想文のコサイン類似度。マルチモーダル埋め込みを併用する場合は加重平均）

共鳴度 ≥ match_threshold → ペア成立 → 反応名を生成 → フィードへ
```

閾値は `app_settings` テーブルで調整可能（会場の反応を見ながらSQLで即時変更できる）。

### AIキーなしでの動作

| 機能 | キーあり | キーなし |
| --- | --- | --- |
| embedding | OpenAI `text-embedding-3-small` | 文字bigramハッシュによる決定的な擬似embedding |
| 反応名 | Claude (`claude-3-5-haiku`) | 2つの感想の断片を組み合わせた短句 |

どちらも体験は成立するが、共鳴の質は落ちる。本番はキーを設定すること。

## Devin・Supabaseの活用について

### Devin

3日間で複数セッションに分け、要件をドキュメント化した上でDevinに実装を任せる形で開発を進めた。

- **マイルストーン単位でのセッション分割**：非同期処理化とテスト基盤整備、共鳴フィードのUI実装、
  演出の作り込みなど、依存関係のある作業はまとめて1セッション内で連続実装し、独立した作業は
  セッションを分けることで、指示の一貫性と実行効率を両立させた
- **実装→プレビュー確認→フィードバック→修正、のサイクルを高速で回した**：VercelプレビューデプロイをDevinに都度用意してもらい、実際に動く画面を見ながら「意味が伝わらない」「テンポが悪い」といった
  UXフィードバックを言語化し、次のセッションの指示に反映するというサイクルを繰り返した
- **テスト基盤自体もDevinに実装させた**：実際の参加者データを待たずに共鳴の発生を検証できる、
  強制ペア投入・強制マッチ投入の仕組みをDevinに構築してもらい、以降の機能検証を高速化した
- **インフラ操作も一任**：Supabaseへのスキーマ適用・シード投入、Vercelへのデプロイ、
  環境変数（Secrets）の設定まで、認証情報を都度セッション限定で渡す形でDevinに任せた

### Supabase

Postgres・pgvector・Realtime・Edge Functionsを、それぞれ以下の役割で活用した。

- **Postgres + pgvector**：参加者の感想文をembeddingに変換して保存し、コサイン類似度による
  リアルタイムな近傍検索で「共鳴度」を算出する中核部分に使用
- **Realtime**：`matches`テーブルへのinsertを`postgres_changes`で購読し、ページ再読み込みなしで
  共鳴フィード・星座UIに即座反映させた。会場での「今まさに繋がりが生まれた」体験を支える基盤
- **Edge Functions**：感想投稿の受け口（`submit-response`）や共鳴判定処理をサーバーレスで実装。
  外部AIサービス（OpenAI/Claude/Gemini）呼び出しもここに集約した
- **Table Editor**：会場運営用の管理画面を自作せず、刺激画像・ヒント語などの運用データを
  Supabase標準のTable Editorから直接編集する運用にすることで、開発工数をコア機能に集中させた

### 1. Supabaseプロジェクトを用意する
Supabaseでプロジェクトを作成し、`supabase db push`でスキーマを適用する。

### 2. 環境変数を設定する
`.env.local`に以下を設定する。

```
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
OPENAI_API_KEY=       # 任意（未設定時はフォールバック動作）
ANTHROPIC_API_KEY=    # 任意（未設定時はフォールバック動作）
GEMINI_API_KEY=       # 任意（マルチモーダル埋め込みを使う場合）
```

### 3. 依存関係をインストールし、開発サーバーを起動する
```
npm install
npm run dev
```

## 運営当日の流れ

1. 開場前に `/admin/stimuli` で使う刺激を登録する（`/respond` には表示ONの刺激が並ぶ）
2. 会場の大画面に `/screen` を出しておく
3. 参加者はスマホで `/` → `/respond`
4. フィードの流れが鈍いときは `match_threshold` を下げる（下記）
5. 進行に合わせて `/admin/stimuli` で表示ON/OFFを切り替える

## 調整可能なパラメータ

`app_settings` テーブルをSQLで更新するだけで反映される：

| パラメータ | 説明 | 初期値 |
| --- | --- | --- |
| `match_threshold` | 共鳴と判定する類似度の閾値 | 0.90前後（要調整） |
| `text_weight` | テキストembedding類似度の重み | 1.0（診断スコア廃止に伴い実質固定） |
